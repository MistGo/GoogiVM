`custom_loadstring_full.lua` is **GoogiVM**: a single-file Lua 5.1 compiler, peephole optimizer, and register/stack virtual machine written in 100% pure Lua. It requires zero external dependencies and never touches `load`, `loadstring`, FFI, `debug`, `io`, or `os`.

It is designed for game modding environments (such as **Scrap Mechanic / ScrapComputers**), embedded scripting engines, and restricted sandboxes that need to compile and run Lua 5.1 source strings safely and quickly.

> **Single-file deployment:** Only `custom_loadstring_full.lua` is required at runtime. The `tests/` directory and benchmark files are for development only.

## Why GoogiVM?

Most pure-Lua interpreters (such as **FiOne** / **LBI**) are *bytecode-only* interpreters: to run Lua source code, you must first run a separate pure-Lua lexer/parser/compiler (`LuaZ`/`LuaX`/`LuaY`/`LuaK`/`LuaU` from Yueliang) to serialize Lua 5.1 bytecode, and then deserialize and interpret it in FiOne.

**GoogiVM** replaces that entire multi-file chain with a single integrated pipeline:

```text
Lua 5.1 Source
  -> Streaming Lexer & Single-Pass Compiler (no AST allocation)
  -> Per-Function Prototype + Line Table
  -> Linear Peephole Superinstruction Optimizer (Opcodes 52-168)
  -> Explicit-Frame Stack/Register VM (Balanced Opcode Dispatch Tree, Frame Pooling, Tail-Call Optimization)
```

### Key Features

- **Complete Lua 5.1 Language Support:**
  - Control flow: `if`/`elseif`/`else`, `while`, `repeat`/`until`, numeric `for`, generic `for`, `break`, `do`/`end`, `return`.
  - Functions & closures: lexical scoping, mutable upvalues (heap-cell backpatching), varargs (`...`), method syntax (`obj:method()`), and **frame-reusing tail calls (`return f(...)`)**.
  - Tables & metamethods: array/hash/nested constructors, multi-return tail expansion (`{a, f()}`), and full host metamethod support (`__index`, `__newindex`, `__add`..`__pow`, `__eq`, `__lt`, `__le`, `__concat`, `__unm`, `__call`, `__len`).
  - Environments: isolated per-chunk `env`, plus sandboxed `getfenv`/`setfenv` support for interpreted closures.
- **Built-in Sandbox Quotas & Safety:**
  - Configurable compile-time limits (`maxSourceBytes`, `maxCodeSlots`) and runtime budgets (`maxInstructions`, `maxCallDepth`, `maxStack`, `maxArgs`, `maxReturns`).
  - Blocks `getfenv`/`setfenv` on native C/host functions and `setfenv(0, ...)`, including when they are reached through guest `pcall`/`xpcall`, so untrusted code cannot escape into the host `_G`.
- **Source-Line Tracebacks:**
  - Syntax errors report exact line numbers and nearby tokens.
  - Runtime errors are rewritten to `sourceName:line: message` with a full call-stack traceback across interpreted frames.
  - Guest `pcall`/`xpcall` around interpreted closures keep the same sandbox format: host file paths and internal VM line numbers are never exposed.
- **Bounded Stack for Tail Calls:**
  - `return f(...)` reuses the current frame **and** its original stack region, so even millions of tail calls stay within a constant `maxStack` footprint.
- **Superinstruction Peephole Optimizer (92 Fused Opcodes):**
  - Fuses local moves, constant loads, binary arithmetic, compound assignments (`s = s + i`, `s = s + t[i]`, `s = (s + i) % k`, `t[i % k] = v`), multiple-assignment swaps (`a, b = b, a`), table reads/writes (`t[k] = v`, `t.field = v`), short-circuit comparisons (`and`/`or`), conditional branches (`if a < b`, `if x % d == 0`), numeric `for` bodies (including `s = s * k`, `s = s % k` and `s = s .. k`), per-iteration closures, table constructors, and `ipairs`/`pairs` generic `for` loops that run the iterator and the loop step inside one dispatch (`TFOR_1`/`TFOR_2`) instead of a dispatch-heavy sequence.
  - Opcode families share a single opcode with a *kind* stored in a dead slot, so the dispatch tree stays small: all twelve comparison branches, all seven compound assignments, and the whole `and`/`or` test family each cost one opcode instead of six to eighteen.

## Quick Start

Copy `custom_loadstring_full.lua` into your project and load it:

```lua
local custom_loadstring = dofile("custom_loadstring_full.lua")

local env = {
    ipairs = ipairs,
    pairs = pairs,
    next = next,
    select = select,
    tostring = tostring,
    tonumber = tonumber,
    type = type,
    pcall = pcall,
    xpcall = xpcall,
    assert = assert,
    error = error,
    math = math,
    string = string,
    table = table,
}

local chunk, err = custom_loadstring([[
    local out = {}
    for i = 1, 5 do
        out[i] = i * i
    end
    return table.concat(out, ", ")
]], env, {
    sourceName = "example.lua",
    maxInstructions = 1000000,
})

if not chunk then
    error("Compile error: " .. tostring(err))
end

print(chunk()) --> 1, 4, 9, 16, 25
```

If `env` is omitted (`nil`), GoogiVM creates a **fresh empty table `{}`** — it never exposes the host `_G` by default.

## Public API

```lua
local chunk, err = custom_loadstring(source, env, options)
```

| Parameter | Type | Description |
|---|---|---|
| `source` | `string` | Lua 5.1 source code to compile. Non-strings return `nil, "script must be a string"`. |
| `env` | `table \| nil` | Global environment table for the chunk (`nil` creates a new `{}`). |
| `options` | `table \| nil` | Optional configuration and resource budgets (see below). |

**Return values:**
- **Success:** returns a callable Lua function `chunk(...)`.
- **Failure:** returns `nil, err` where `err` is a human-readable syntax or option validation error.

### Options & Resource Limits

All limits are enabled by default and can be customized per chunk or disabled individually by passing `math.huge`:

| Option | Default | Description |
|---|---:|---|
| `sourceName` | `"<string>"` | Chunk name shown in runtime error messages and stack tracebacks. |
| `maxSourceBytes` | `4,194,304` (4 MiB) | Maximum allowed length of `source` in bytes. |
| `maxCodeSlots` | `8,388,608` | Maximum bytecode array numbers per compiled function prototype. |
| `maxInstructions` | `50,000,000` | Maximum VM instructions executed per top-level call to `chunk(...)`. |
| `maxCallDepth` | `10,000` | Maximum nested interpreted call frames (tail calls reuse frames and do not count). |
| `maxStack` | `1,000,000` | Maximum VM register/expression stack index. |
| `maxArgs` | `1,000` | Maximum arguments passed to a function call. |
| `maxReturns` | `1,000` | Maximum return values produced by a function return or vararg expansion. |

## Host-dependent semantics

GoogiVM implements the Lua 5.1 **language**, but a few behaviors are defined by
the host runtime and are inherited rather than re-implemented. They are listed
below so that "Lua 5.1 compatible" is not read as "host-independent standard
library":

| Area | Behavior |
|---|---|
| `#` on tables with holes | Follows the host's length algorithm; it is not defined as "highest integer key". |
| `__len` | Honored only when the host honors `__len` for tables (Lua 5.2+ do; LuaJIT in 5.1 mode and plain Lua 5.1 do not). |
| `getfenv` / `setfenv` | Available only when the host provides them. Interpreted closures (including numeric levels) are fully supported; `setfenv(0, ...)` is rejected and native function environments are blocked. |
| Numeric formatting | `tostring(number)` uses the host formatter. |
| Libraries | Only what you place in `env`; GoogiVM never imports `math`, `string`, or `table` itself. |
| Metamethod dispatch | Performed by host operators, so host-specific `__eq`/`__lt`/`__le`/`__concat` quirks apply. |
| Operator error text | Produced by the host; GoogiVM only rewrites the location prefix to `sourceName:line`. |
| Restricted sandboxes | GoogiVM needs host `setmetatable` and `getmetatable` at load time (weak caches and the `__add` fast path). Hosts that proxy them, such as Scrap Mechanic, must supply the proxied versions. `rawget`, `rawset` and `rawequal` are never used, so their absence is harmless. |

If you need bit-identical behavior, run the same host version everywhere;
GoogiVM does not ship a second standard library.

## Performance Benchmarks

### 50-Case Head-to-Head Suite (`BENCHMARK_50.md`)

Across 50 diverse microbenchmarks comparing **GoogiVM** against upstream **FiOne** (`SovereignSatellite/FiOne` running precompiled `luac5.1` bytecode). Every figure below is the **median of 10 consecutive full runs** of the suite on the same machine; each run itself records the median of 7 measured iterations after 3 warm-up iterations:

- **48 wins**, **no losses**, **2 near-ties** (within 5%).
- **4.74x faster by total median execution time** (`1.0393 s` vs `4.9249 s`).
- **2.45x geometric mean speedup** across all 50 workloads.

Ten runs are used instead of three because small samples are outlier-sensitive: a single run disrupted by the OS scheduler or the garbage collector can move a mean by tens of percent. Median, trimmed mean (fastest and slowest run dropped) and plain mean agree within a few percent on this sample — `4.74x` / `4.65x` / `4.62x` total, `2.45x` / `2.43x` / `2.42x` geometric mean — so the result is stable.

Absolute seconds move with host load, so they are not comparable across sessions: an earlier session measured the same code roughly 1.5x faster in absolute terms while the ratios stayed within a few percent. The ratio columns are the stable metric.

Per-category median ratios:

| Category | FiOne / GoogiVM | Notes |
|---|---:|---|
| Function calls | 5.73x - 6.68x | `calls_threearg_500k` 5.73x, `method_call_100k` 6.68x |
| Closures / upvalues | 1.03x - 9.70x | `closure_upvalue_1m` 9.70x, `closure_loop_capture_100k` 1.76x, `closures_create_100k` 1.03x |
| Recursion (incl. tail) | 1.33x - 13.71x | `recursion_fact_10` 1.33x, `mutual_recursion_1000` 13.71x, `tail_recursion_1000` 12.73x |
| `ipairs` / `pairs` / `next` | 1.61x - 4.24x | `generic_next_100k` 1.61x, `generic_ipairs_50k` 4.24x |
| Metatables | 9.38x | `metatable_add_100k` |
| Only non-wins | 0.95x - 1.03x | `branch_and_or_100k` 0.95x, `closures_create_100k` 1.03x |

The geometric mean of **2.45x** is the honest aggregate: it is dominated by the sub-millisecond cases, which are the noisiest. The two cases outside the 5% win band are both allocation- or micro-timing-bound rather than dispatch-bound. `closures_create_100k` allocates a fresh closure per iteration — a native Lua function, a per-closure record and an entry in a weak-key registry — so it lands at parity. `branch_and_or_100k` is already down to a five-dispatch loop body, and its whole measurement is a few milliseconds, so it flips around parity between sessions.

### Reproducing the suite

[`benchmarks/bench50_actual.lua`](benchmarks/bench50_actual.lua) regenerates both files. Run it from the repository root:

```bash
luajit benchmarks/bench50_actual.lua <path-to-FiOne/source.lua> <dir-with-luac5.1> [work-dir]
```

It needs a [FiOne](https://github.com/SovereignSatellite/FiOne) checkout and a Lua 5.1.5 compiler, because FiOne consumes `luac5.1` bytecode. The three arguments can also come from the `FIONE_PATH`, `LUAC_DIR` and `BENCH_DIR` environment variables; the defaults are `./FiOne/source.lua`, the current directory, and `./bench50-work`.

Compilation happens outside the timer, so the numbers are execution time only. The script writes `BENCHMARK_50.md`, `BENCHMARK_50.csv` and an untracked `BENCHMARK_50_raw.csv` with every individual sample to the current directory. A full run takes about two and a half minutes.

A single run is a small sample, so the published figures come from **10 consecutive runs** of that command (rename each `BENCHMARK_50.csv` to `run1.csv` … `run10.csv`), aggregated with [`benchmarks/median_report.lua`](benchmarks/median_report.lua):

```bash
luajit benchmarks/median_report.lua run1.csv … run10.csv
```

It takes the per-case median across runs, reports wins/losses/ties on a 5% tie band, the geometric mean, and writes the aggregated `BENCHMARK_50.md` and `BENCHMARK_50.csv`. Never run two suites at the same time — the CPU contention makes the numbers meaningless.

Note that this suite runs under **LuaJIT with the JIT enabled**. That is the right profile for comparing two interpreters on equal terms, but it is not the profile GoogiVM runs in inside Scrap Mechanic, where the JIT never compiles the VM's own dispatch loop. The suite below measures that second profile.

### Real-world suite (the game profile)

[`benchmarks/benchreal.lua`](benchmarks/benchreal.lua) runs 16 full workloads adapted from [The Computer Language Benchmarks Game](https://benchmarksgame-team.pages.debian.net/benchmarksgame/) — `nbody`, `spectral-norm`, `mandelbrot`, `binary-trees`, `fannkuch-redux`, `pidigits`, `fasta`, `k-nucleotide`, `sieve`, `queens`, `matmul`, `quicksort`, `wordfreq`, `oop`, `jsonencode`, `hanoi`. These are complete programs rather than microbenchmarks, so they are much closer to what a computer program in a mod actually does. Every case returns a value that is checked against a known expectation, so a wrong result is reported instead of silently timed.

```bash
luajit -joff benchmarks/benchreal.lua      # the in-game profile
luajit benchmarks/benchreal.lua            # the JIT profile
```

Medians of three runs on one machine, seconds:

| Engine | Total |
|---|---:|
| Native PUC Lua 5.1 (reference only) | 0.467 |
| **GoogiVM, JIT enabled** | **2.343** |
| **GoogiVM, `-joff` (game profile)** | **6.902** |
| Upstream FiOne, `-joff` | 7.763 |

Against FiOne that is **3.31x** with the JIT on and **1.12x** with the JIT off. The difference is structural: with the JIT, GoogiVM's dispatch loop becomes machine code; with `-joff` every VM instruction costs a host interpreter dispatch, while FiOne — already a pure interpreter — is unaffected by the flag. This is the honest number for Scrap Mechanic.

Under `-joff` the suite is **5 wins, 10 losses, 1 tie**: it wins `binary-trees` 1.66x, `hanoi` 1.60x, `oop` 1.47x, `spectral-norm` 1.38x and `jsonencode` 1.34x, ties `fasta`, and loses `sieve` 0.49x, `fannkuch-redux` 0.60x, `quicksort` 0.67x, `mandelbrot` 0.68x, `wordfreq` 0.69x, `k-nucleotide` 0.70x, `pidigits` 0.75x, `matmul` 0.80x, `queens` 0.80x and `nbody` 0.89x. The split is consistent: work that is dominated by calls, tables and allocation favours the fused dispatcher, and tight numeric kernels — where almost every source statement is a single arithmetic instruction — favour the smaller per-instruction cost of a bytecode interpreter. Against the native PUC Lua 5.1 interpreter GoogiVM is about 14.8x slower, which is the expected cost of interpreting Lua bytecode from inside Lua.

## Architecture Overview

See [`TECHNICAL.md`](TECHNICAL.md) for a deep dive into the compiler, bytecode format, and VM internals.

1. **Lexer & Single-Pass Parser:**
   - Scans tokens on demand (`tk`, `tv`, `tp`, `pos`) without building a token list or AST.
   - Tracks newline offsets in `line_starts` and resolves source lines via binary search (`line_of`).
2. **hybrid Stack + Register Bytecode:**
   - Locals live in fixed frame-relative registers `S[base + slot - 1]`.
   - Temporary expression values use the top of `S` above `base + maxreg - 1`.
   - Captured locals are automatically promoted to heap cells (`{ v = val }`) by backpatching `NOP -> CELL` and `GETLOCAL/SETLOCAL -> GETCELL/SETCELL`.
3. **Peephole Superinstruction Optimizer (`optimize_code`):**
   - Scans jump targets first so it never fuses across a branch destination.
   - Replaces multi-instruction sequences in place (marking trailing slots dead and advancing `pc` by `4 * len`).
   - Fuses loop control (`FORLOOP_MOV`, `FORLOOP_CELL`) with hot loop bodies (`FORLOOP_ADD_RR/RK`, `FORLOOP_SUB_RR/RK`, `FORLOOP_ASSIGN_RR/RK`, `FORLOOP_ADD_INDEX`, `FORLOOP_SETINDEX_RR/RK`, `FORLOOP_MOD_RR_EQ_K`, `FORLOOP_NEWTABLE_SETINDEX_R`).
   - Fuses generic `for` loops into `TFOR_1` and `TFOR_2` with direct in-VM `ipairs` and `next` iteration.
4. **Explicit Call Frames & Frame Pool:**
   - Custom-to-custom function calls (`CALLD`) push a lightweight frame onto `frames[]` (reusing pooled frame tables from `free_frames`) and jump to `pc = 1` inside the same `while true` loop — avoiding host Lua C-stack recursion.
   - Tail calls (`return f(...)`) overwrite the current frame in place.
