# Техническое описание

Краткое руководство по внутреннему устройству LuaSandbox VM. Использование описано в [`README.ru.md`](README.ru.md).

Вся реализация находится в одном файле: `custom_loadstring_full.lua`. В нём лексер, парсер, эмиттер байткода, peephole-оптимизатор и виртуальная машина.

## Конвейер

```text
исходник Lua
  -> встроенный лексер + рекурсивный парсер
  -> прототипы функций с байткодом
  -> линейный peephole-оптимизатор
  -> нативное замыкание Lua + weak-метаданные
  -> стековая VM с явными кадрами
```

AST нет. Парсер emit-ит байткод прямо во время разбора.

## Компилятор

Лексер хранит только текущий токен (`tk`), его значение (`tv`), позицию (`tp`) и позицию сканера (`pos`). Массива токенов нет.

Каждая функция компилируется в контекст кадра (`fc`):

- `code` — плоский массив байткода;
- `consts` — таблица констант с индексацией от 1;
- `locals` — активные описания локальных;
- `upvals` — описания захваченных upvalue;
- `nextreg` / `maxreg` — распределение регистров;
- `loop_breaks` — ожидающие переходы `break`.

Базовая инструкция — четыре числа:

```text
[OPCODE, A, B, C]
```

Локальная переменная занимает регистр относительно кадра. Если вложенная функция её захватывает, компилятор:

1. заменяет `NOP`-заглушку на `CELL`;
2. переписывает `GETLOCAL`/`SETLOCAL` в `GETCELL`/`SETCELL`;
3. делит получившуюся ячейку `{ v = value }` с вложенным замыканием.

Прототипы функций лежат в общем списке. Корневой чанк — тоже прототип, vararg, без фиксированных параметров.

## Байткод

Обычные опкоды — **1–51**. Fused-опкоды, создаваемые оптимизатором, — **52-119**:

| Диапазон | Назначение |
|---:|---|
| 52–57 | перемещение локальных и простые записи |
| 58–69 | арифметика с регистром/константой |
| 70–87 | сравнения |
| 88–94 | чтение/запись таблиц и индексов |
| 95–101 | шаблоны составного присваивания |
| 102–109 | условные переходы |
| 110-118 | копирование переменной числового `for` and fused loop-body operations |
| 119 | fused modulo/equality branch |

Байткод приватный. Он не сериализуется, не имеет стабильного ABI и не должен сохраняться между версиями.

## Peephole-оптимизатор

`optimize_code` запускается после полной компиляции функции. Сначала он собирает цели переходов, затем склеивает частые последовательности инструкций.

Главное правило: **оптимизатор не сдвигает код**. Он записывает fused-инструкцию в первый слот, а следующие помечает мёртвыми. VM перепрыгивает мёртвые слоты:

- 2 слота → `pc + 8`;
- 3 слота → `pc + 12`;
- 4 слота → `pc + 16`;
- 6 слотов → `pc + 24`.

Слияние никогда не пересекает цель перехода. `can()` проверяет карты целей и мёртвых слотов до применения шаблона.

Оптимизатор также сворачивает копирование переменной числового `for` в `FORLOOP_MOV` или `FORLOOP_CELL`. Первая итерация ещё использует копирование в теле; последующие обрабатывает опкод цикла.

Для самых горячих числовых циклов первая операция тела тоже сворачивается в опкод цикла: `sum = sum + i`, `t[i] = i`, `sum = sum + t[i]` и похожие шаблоны. Опкод цикла выполняет инкремент, операцию тела и следующий диспетчерский переход за одну итерацию VM. Конструкция `(value % K) == K2`, за которой идёт условный переход, сворачивается в `JMPF_MOD_EQ_K`, что также убирает промежуточные операции со стеком.

## VM

При вызове верхнего уровня создаются:

- `S` — общий стек значений;
- `top` — вершина стека;
- `frames` — явные кадры вызовов;
- `base` — база текущего кадра;
- `pc` — счётчик инструкций;
- `C`, `K`, `U` — код, константы, upvalue;
- `e` — текущее окружение.

В цикле диспетчеризации эти значения продублированы в локальные переменные: табличные обращения к состоянию VM были бы слишком дорогими.

### Вызовы

Все вызовы идут через `CALLD`:

- регистр-маркер хранит позицию функции в стеке;
- аргументы лежат выше значения функции;
- число результатов: `-1` — все, `0` — ни одного, `n` — ровно `n`.

Для пользовательского замыкания VM добавляет явный кадр, сдвигает аргументы в слоты параметров, очищает локальные регистры вызываемого и продолжает тот же цикл. Вызовы «свой → свой» не рекурсируют через хост на каждый вызов.

Вызов `return f(...)` помечается в неиспользуемом операнде `C` у `CALLD`. Для интерпретируемой цели VM заменяет текущий кадр, перенося `ret_sp` и `wanted`; для native-цели результаты переносятся в область выражений и следующий `RET` снимает текущий кадр. Это tail-call optimization без изменения обычного протокола вызовов.

Нативные функции используют быстрые пути для 0/1/2 аргументов и `unpack` для остальных.

### Замыкания и множественный возврат

Замыкание — настоящая функция Lua; метаданные прототипа/upvalue/окружения лежат в weak-таблице `closure_info`. Upvalue указывают на ячейки, если значение общее.

Для множественного возврата используются `MARK`, `POP`, `PEEK`, `VARARG` и `SETLISTMULTI`. Компилятор отслеживает `top_multi` / `last_multi_pc` и патчит число результатов, когда контекст списка выражений известен.

### Таблицы и метаметоды

Чтение и запись таблиц идут через обычные `t[k]` хоста. Арифметика, сравнения, конкатенация, длина и `__call` поэтому используют метаметоды хоста; второго движка метаметодов в VM нет.

### Окружение

Глобальное чтение и запись идут напрямую в таблицу `env`, поэтому `__index` и `__newindex` работают. По умолчанию это пустая таблица, а не `_G`.

`getfenv`/`setfenv` специально обрабатываются в `CALLD`, если они есть в хосте. `setfenv(0, ...)` намеренно запрещён. Окружение native-функций через sandbox недоступно: `getfenv(nativeFn)` и `setfenv(nativeFn, ...)` выбрасывают ошибку.

### Бюджеты

`custom_loadstring` принимает необязательный третий аргумент `options`. На этапе компиляции проверяются размер исходника и число слотов байткода. Во время выполнения проверяются число инструкций, глубина интерпретируемых вызовов, индекс стека значений, число аргументов и возвратов. Все лимиты включены по умолчанию; отдельный лимит можно отключить через `math.huge`.

### Совместимость с LuaJIT

LuaJIT 2.1 иногда неправильно компилирует базовый путь сравнений внутри большой функции VM при длительных fuzz-нагрузках. Поэтому базовые сравнения идут через небольшую функцию, для которой явно вызывается `jit.off`, если доступен API `jit`, а fused-сравнения порядка на таких хостах отключаются. Fused-проверки равенства и неравенства остаются включёнными. Арифметика и циклы по-прежнему выполняются JIT.

### Ошибки и карта строк

Синтаксические ошибки ловятся через `pcall(compile)` и возвращаются как `nil, message`. Каждый прототип хранит `sourceName` и таблицу `lines`. Строковые ошибки выполнения получают `sourceName:line` и короткий стек интерпретируемых кадров; таблицы-ошибки сохраняются без изменений.

## Изменение реализации

Перед добавлением fused-опкода:

1. выбери свободный номер и добавь его в `FOP`;
2. добавь ветку в `run_closure`;
3. добавь шаблон в `optimize_code`;
4. согласуй шаг `pc` с `put()`;
5. добавь тест в `tests/test_superinstructions.lua`;
6. прогони обе команды тестов из README.

Никогда не сливай инструкции через цель перехода и не пропускай живые инструкции.

## Известные ограничения

- Нет таймаута по времени и квоты памяти; бюджеты инструкций/глубины/стека есть, но внешняя изоляция всё ещё рекомендуется.
- Нет сериализации байткода.
- Нет грамматики Lua 5.2+.
- Обычная (не tail) рекурсия ограничена `maxCallDepth` и стеком значений VM; `return f(...)` переиспользует текущий кадр.
- Поведение `#` на разреженных таблицах и часть краевых случаев метаметодов определяется хостом.
